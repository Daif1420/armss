# ARMS Backend & Database — v1

This ZIP contains a runnable Next.js server project and an initial Supabase/PostgreSQL schema with an atomic Excel import RPC.

## Setup
1. Create a Supabase project.
2. Open SQL Editor and run `supabase/schema.sql` in a new project.
3. Copy `.env.example` to `.env.local`.
4. Set `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` in the server environment only.
5. Run `npm install`, then `npm run dev`.
6. Open `/api/health`. Upload a workbook by sending `multipart/form-data` with a `file` field to `POST /api/import`.

## Excel import behavior
- Prefers sheet `البيانات (2)`, then `بيانات المشاريع`, then first worksheet.
- Recognizes Job ID, Job Name, Branch Name, Total Boxes, Total Documents, Total Sheets, and Date Of Delivery aliases.
- Validates IDs/numeric fields, skips duplicate IDs within the uploaded file, and returns row-level validation errors.
- Existing projects are matched by Job ID. New projects are inserted. Changed source values are flagged `Changed` and logged, while existing project status and archive placement are preserved.
- A project absent from an upload is NOT marked Missing automatically.

## Important production notes
- This is backend/database v1, not a fully deployed production system.
- Authentication/authorization for the import endpoint must be added before exposing it publicly. As written, protect the route behind your trusted admin authentication/reverse proxy before real use.
- Box/dossier auto-allocation and the confirmed D41/D42 start sequence are not auto-generated by this version. This is intentional: the precise approved sequence and existing archive assignments must be seeded and tested before allocation.
- SQL schema enables RLS but intentionally does not create permissive client policies. Do not expose the service role key to browser code.
- Test on a separate Supabase project and backup the source workbook before importing production records.


## ARMS Requirements Alignment (v2)

This package includes `supabase/migrations/003_arms_requirements_alignment.sql` for the strict archive lifecycle:
- Project: `Archived`, `Missing`, `Pending`
- Dossier: `Pending`, `Inprogress`, `Archived`
- Box: `Inprogress`, `Archived`
- Separate Force Closed flag/event (not a Box status)
- Expected sequential 6 × 50 project slots for configured 300-project boxes
- `date delivery` / `Date Approved` synchronization
- Expanded role values for System Admin, Archive Manager, Data Entry, and Viewer

**Deployment:** Back up your Supabase database first, then apply this migration after `supabase/schema.sql`. Verify the archive ranges before applying because it creates expected project-slot records for configured boxes. Printed labels use English field text.

## v2 code alignment (fix)
Application code now matches migration 003: project statuses are `Archived / Pending / Missing`, dossier/box statuses are derived by the DB (`Pending|Inprogress|Archived`, `Inprogress|Archived`), and Force Close is a separate flag + `force_close_events` row (action `close` = force close, `reopen` = remove the flag). Imports and box creation call `arms_create_expected_slots` / `arms_recalculate_box`. Roles: System Manager/System Admin, Archive Manager, Data Entry, Supervisor, Viewer, User.
Note: `arms_recalculate_box` re-derives project statuses from imported data, so manual status edits are overwritten on the next recalculation.
